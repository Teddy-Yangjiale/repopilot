# RepoPilot 检索评测方法

这份文档定义 RepoPilot 的**第一把尺子**：给定一个真实 issue，系统能否指出这次修复实际改动的文件。

没有这把尺子，任何「换成 BM25 会更好」「加 LLM 扩展有用」的说法都无法证伪。所有后续阶段的改动都必须先在这里报出数字。

## 1. 任务定义

**输入**：一个 GitHub issue 的标题和正文（issue 作者写下它时并不知道该改哪个文件）。

**输出**：一个按相关性排序的文件路径列表。

**标准答案**：关闭该 issue 的那个**已合并 PR** 所改动的源文件。

选这个定义的理由：标准答案不是人工标注的，而是仓库维护者用一次真实的代码评审背书过的。没有标注者主观性，也没人能争论「这个答案对不对」。

## 2. 数据集构建

```bash
.venv/bin/repopilot dataset-build \
  --clone /home/teddy/opencv \
  --out datasets/opencv-issues.jsonl \
  --limit 60
```

通过 GitHub GraphQL 的 `closedByPullRequestsReferences` 拿到 issue → PR 链接。走 `gh` CLI 而不是自己发 HTTP：**认证留在你已有的 `gh auth` 会话里，Token 不进入代码、不进入 `.env`、不进入数据集**。

### 过滤规则与理由

| 规则 | 理由 |
|---|---|
| PR 必须是 `merged` | 未合并的 PR 没有被维护者背书，不能当标准答案 |
| PR 改动文件数 ≤ 10 | 40 个文件的大重构不是「定位」任务，任何排序都无意义 |
| 只保留源码扩展名 | `.md` / `.yaml` 改动不是代码定位目标 |
| issue 正文 ≥ 80 字符 | 空正文没有可检索的信息，测的是运气 |
| 同一个 PR 只取一次 | 一个 PR 关闭 3 个 issue 会让这次修复的权重变成 3 倍 |
| 标准答案文件必须在评测快照中仍存在 | 文件已被重命名或删除时，任何检索器都不可能返回它 |

每次构建都会打印各条规则丢弃了多少 issue。**一个不能被审计的数据集不能证明任何事。**

## 3. 指标

三个指标回答三个不同的问题，它们的分歧本身就是信息：

- **Recall@k** —— 这次修复涉及的文件，有多大比例出现在前 k 个？惩罚「只找到一半」。
- **Hit@k** —— 前 k 个里**有没有**一个是对的？这是「有没有给人一条真实线索」的指标。一个 PR 改了 2 个文件，只找到 1 个，Recall@5 = 0.5 但 Hit@5 = 1.0。对使用者来说后者往往才是决定性的。
- **MRR** —— 第一个正确文件排在多靠前。区分「排第 1」和「排第 9」。

外加 `zero_evidence_rate`（完全零命中的比例）和延迟 p50/p95。

## 4. 已知偏差（必须主动说明）

这三条是当前方法的真实局限，写在这里是为了不让数字被过度解读：

1. **快照评测偏差（乐观）**。所有 case 都在本地仓库的**同一个 HEAD** 上评测，而不是各自 PR 的父提交。也就是说修复代码此刻已经在树里了。正确做法是按 `EvalCase.base_sha` 逐个 case 检出父提交，数据集已经记录了这个字段，留给下一步。

2. **文本泄漏（乐观）**。崩溃报告经常直接贴出出错文件的路径。这是**真实输入而不是作弊**，但它确实抬高分数。因此每个 case 都带 `body_mentions_gold_path` 标记，报告同时给出「全部 case」和「正文未提及标准答案文件」两栏。**后一栏才是诚实的下界。**

3. **幸存者偏差（乐观）**。标准答案文件在今天已不存在的 case 被丢弃了，这让数据集偏向长期稳定的文件。

三条偏差都指向同一个方向：**真实的线上表现只会比这些数字更差，不会更好。**

## 5. 基线结果（2026-08-13）

数据集 `datasets/opencv-issues.jsonl`，60 个 case，仓库 `opencv/opencv` @ `f1e824b88a`，策略 `deterministic`（不调用任何模型）。

| 指标 | 全部 60 case | 正文未提及答案文件（26 case） |
|---|---:|---:|
| Recall@1 | 0.058 | 0.077 |
| Recall@5 | 0.175 | 0.154 |
| Recall@10 | 0.183 | 0.173 |
| Hit@1 | 0.083 | 0.115 |
| Hit@5 | 0.267 | 0.192 |
| Hit@10 | 0.283 | 0.231 |
| MRR | 0.170 | — |
| 零命中率 | 0.000 | — |
| 延迟 p50 / p95 | 3391 ms / 3753 ms | — |

**消融：正文预算**。`--body-chars 0`（只用标题）与 `--body-chars 600` 的所有指标完全相同。原因是确定性抽取器取正则匹配的**前 6 个** token，而 OpenCV issue 模板的正文开头是 `System Information / OpenCV version` 这类样板词。多喂的 600 字符只贡献了 `System`、`Information`、`version`、`Description` 这些噪音词（14/60 个 case 关键词有变化，指标零变化）。**正文里真正有价值的堆栈和符号，当前抽取器永远够不到。**

### 失败模式诊断

这个基线不是「差」，而是**差得非常有规律**：

| 现象 | 数字 |
|---|---:|
| `3rdparty/libtiff/ChangeLog` 出现在 top-3 | 38 / 60 个不相关 case |
| top-3 预测里属于 `3rdparty/` 的比例 | 61.1% |
| 标准答案里属于 `3rdparty/` 的比例 | **0.0%** |
| 标准答案**从未被检索到**（召回问题） | 22 / 60 |
| 检索到但**排名 > 10**（排序问题，中位排名 16） | 21 / 60 |
| 检索到且排名 ≤ 10（即 Hit@10） | 17 / 60 |

三个根因，各自对应一个明确的下一步：

1. **没有 IDF**。抽取器把 `Pointer`、`overflow`、`allocation`、`width` 这种通用英文词和 `icvCvt_BGRA2RGBA_16u_C4R` 这种唯一符号同等对待。排序按「匹配了几个不同关键词」算分，于是一个包含所有常见英文词的巨大 ChangeLog 稳定击败只匹配了那一个精确符号的源文件。→ **BM25 / IDF 加权**。
2. **没有文档长度归一化**。500KB 的变更日志天然匹配更多词。→ **长度归一**。
3. **没有路径先验**。`3rdparty/` 是 vendored 依赖，在这 60 个 case 里**从来不是**修复位置。→ **路径先验或直接降权**。

失败被清楚地劈成两半，各占约三分之一：

- **21/60 是排序问题** —— 正确文件已经在候选集里，只是排名 > 10。不改检索、只改排序就能救回来。这部分决定了**纯排序改进的天花板是 Hit@10 = 0.633**（把这 21 个全部提进前 10）。
- **22/60 是召回问题** —— 正确文件从头到尾没被检索到，排序再好也无能为力。只能靠改进关键词抽取（当前取正文前 6 个 token，够不到堆栈里的符号）。

结论：**先做排序**（单项收益最大、成本最低、不碰检索路径），**再做关键词抽取**。这是有实测支撑的优先级，不是拍脑袋。

## 6. 阶段 B 结果：路径先验 + IDF（2026-08-13）

同一数据集、同一快照、同一批关键词，只改排序。四个消融臂：

| 排序配置 | Recall@1 | Recall@10 | Hit@1 | Hit@10 | MRR | Hit@10（无泄漏子集） |
|---|---:|---:|---:|---:|---:|---:|
| 阶段 A 基线 | 0.058 | 0.183 | 0.083 | 0.283 | 0.170 | 0.231 |
| 仅全池打分 | 0.075 | 0.303 | 0.117 | 0.400 | 0.180 | 0.385 |
| + 路径先验 | 0.100 | 0.339 | 0.150 | 0.433 | 0.235 | 0.423 |
| + IDF | 0.108 | 0.427 | 0.150 | 0.567 | 0.270 | 0.423 |
| **+ IDF + 路径先验** | **0.206** | **0.472** | **0.300** | **0.583** | **0.390** | 0.423 |

**Hit@10 从 0.283 到 0.583，Recall@10 从 0.183 到 0.472，MRR 从 0.170 到 0.390。延迟没有变差**（p50 3391ms → 2828ms，因为不再为截断反复回读文件）。

三个信号的贡献可以分开归因：

1. **全池打分（+0.117 Hit@10）**。改动是数据流而非公式：搜索工具原来只返回截断后的 30 条 Evidence，现在同时返回全部命中文件的统计量。正确文件不再会仅仅因为某个常见词先占满引用预算就被丢掉。
2. **IDF（+0.167）**，单项贡献最大。`icvCvt_BGRA2RGBA_16u_C4R` 这类只出现在两三个文件里的符号，权重远高于 `width`、`overflow` 这类到处都是的通用词。
3. **路径先验（+0.016 叠加，但对 top-1 影响很大）**。Hit@1 从 0.150 翻倍到 0.300 —— IDF 负责把正确文件捞进前 10，路径先验负责把 vendored 代码从第 1 名踢开。

### 失败结构的变化

| | 阶段 A | 阶段 B |
|---|---:|---:|
| 正确文件从未被检索到（召回问题） | 22 | 20 |
| 检索到但排名 > 10（排序问题） | 21 | **5** |
| 检索到且排名 ≤ 10 | 17 | **35** |

**排序问题从 21 个降到 5 个** —— 阶段 A 预测的「纯排序天花板 Hit@10 = 0.633」，实测达到 0.583，接近预期。同时**召回问题几乎没动（22 → 20），也和预测一致**：路径先验和 IDF 都不可能救回一个从未被检索到的文件。这验证了当时的诊断，也确认了阶段 C 必须去做关键词抽取。

`3rdparty/` 在 top-3 中的占比从 **61.1% 降到 0.0%**。

### 必须说明的两点

1. **无泄漏子集在 0.423 饱和。** 路径先验、IDF、两者全开在无泄漏子集上的 Hit@10 都是 0.423。也就是说 0.567 → 0.583 那一段增益**主要来自正文提及了答案文件的那批 case**。诚实的说法是：**在最严格的子集上，阶段 B 把 Hit@10 从 0.231 提到 0.423（+83%），而不是提到 0.583。**
2. **新的头部污染来自另一批 vendored 代码。** 现在 top-3 里最常见的是 `modules/ts/include/opencv2/ts/ts_gtest.h`（18/60）—— OpenCV 把 googletest 内嵌在 `modules/ts/` 下，目录名不在通用 vendored 约定表里，所以先验没有覆盖到。**我没有为此加特例**：按仓库特有目录名调参就是在测试集上过拟合。正确解法是让长度归一（B3）或按文件类型的先验来处理，那是可泛化的信号。


## 7. 阶段 C 结果：判别力选词（2026-08-14）

同一数据集、同一快照、同一排序配置（idf+prior），**只改关键词抽取**。阶段 B 的结论是「排序问题 21→5，召回问题 22→20 几乎没动」——回召问题的根因是抽取器：它取正文前 6 个 token，够不到堆栈里的符号。阶段 C 把 `DeterministicKeywordExtractor` 从「首匹配顺序」改为「判别力选词」：

- **符号形状分**：CamelCase / snake_case / 含数字 / 长 token 优先；常见英文词与报告样板词（`System`、`Information`）降权。
- **标题保底**：标题 token 有少量加分（作者写下的核心意图不能被正文符号淹没），但加分必须小——实测 +8 会让「several tests fail」这类泛化标题词挤掉正文真符号（Hit@10 0.750 → 0.650）。
- **正文只挖符号形状 token**：堆栈痕迹（`TiffDecoder::readData`）、函数名进入关键词。
- **编译宏剥离**：`-DOPENCV_*`、`-D_Complex` 这类贴在 issue 里的构建日志宏被清除。
- **符号族去重**：`int32x4_CPP_EMULATOR` 与 `float64x2_CPP_EMULATOR` 是同一测试族的兄弟 case，最后两个下划线段相同的 token 只保留最高分代表——否则 6 个宏会独占全部名额导致零命中。

| 指标 | 阶段 A | 阶段 B | **阶段 C** |
|---|---:|---:|---:|
| Recall@10 | 0.183 | 0.472 | **0.647** |
| Hit@10 | 0.283 | 0.583 | **0.750** |
| MRR | 0.170 | 0.390 | **0.487** |
| Hit@1 | 0.083 | 0.300 | **0.367** |
| 无泄漏子集 Hit@10 | 0.231 | 0.423 | **0.615** |
| 零命中率 | 0.000 | 0.000 | 0.000 |
| 延迟 p50 / p95 | 3391 / 3753 ms | 2828 / 3072 ms | 1911 / 2031 ms |

**失败结构**：召回问题（正确文件从未被检索到）从 20 个降到 8 个。无泄漏子集（正文未提及答案文件，26 case）的 Hit@10 从 0.423 提到 0.615（+45%）——改进不是靠正文直接贴出答案路径，是真实的召回提升。

**诚实的两点**：

1. **延迟下降不归功于本阶段**。关键词抽取不改变逐文件扫描成本；1.9s vs 2.8s 的差异主要来自测量环境（页缓存）与关键词构成。本阶段的卖点是召回，不是速度。
2. **排序问题不再是主要瓶颈**。剩余失败集中在：正文贴的是测试列表/构建日志（判别信号弱）、正确文件在超大生成文件中（长度归一方向性错误，见下）。

**阶段 D 尝试：BM25 长度归一（负收益，已回退）**。为打击 `ts_gtest.h`（22245 行）这类大文件，实现了 BM25 式长度归一并加了消融开关，实测 Hit@10 **0.750 → 0.283**：opencv 语料平均行数仅 430（大量小头文件），正确的核心实现文件（如 `cap_ffmpeg_impl.hpp` 3779 行）远大于均值被降权 85%，小文档被 boost 冲到 top。**长度归一假设「长度≈冗余度」只对网页/新闻类语料成立；代码仓库里大文件=核心实现**。已回退默认关闭，代码与 `--length-norm` 实验开关保留；行数统计已进入搜索协议，留给更合适的归一形式（如按文件类型区分）。

## 8. 快照偏差实测（2026-08-14，base 快照评测）

`--at-base` 模式在官方 `opencv/opencv` 克隆上逐 case 用临时 worktree 检出 PR 的 base commit（修复前代码）评测，与 HEAD 快照对比：

| 指标 | HEAD 快照（乐观） | base 快照（修复前） | 差异 |
|---|---:|---:|---:|
| Hit@10 | 0.767 | 0.733 | -0.034 |
| Recall@10 | 0.664 | 0.608 | -0.056 |
| MRR | 0.487 | 0.410 | -0.077 |
| Hit@1 | 0.367 | 0.267 | -0.100 |
| 无泄漏 Hit@10 | 0.654 | 0.615 | -0.039 |

60 个 case 的 base commit 在官方仓库全部可用（0 缺失；私有 fork 会缺上游历史，已如实标记为 `base_unavailable`）。偏差方向与第 4 节预测一致（乐观），Hit@1 高估最严重（+0.100）。gold 文件在 base commit 上不存在的 case 会被标记（`gold_missing_at_base`）而非静默丢弃。

复现：`repopilot eval --dataset datasets/opencv-issues.jsonl --repo <官方 opencv 克隆> --at-base`。

## 9. Tree-sitter caller-recall 实验（负收益，已回退）

把「文本命中」升级为「调用路径」的第一种尝试：对命中行的外围函数名做二次检索，期望召回调用者。tree-sitter 精确定位函数定义（`utils.cpp:241` → `icvCvt_BGRA2RGBA_16u_C4R`，与文档一致），但函数名作为关键词引入大量调用点/声明/测试噪声：

| 指标 | 基线 | caller-recall | 差异 |
|---|---:|---:|---:|
| MRR | 0.487 | 0.368 | -0.119 |
| Hit@1 | 0.367 | 0.217 | -0.150 |
| Hit@10 | 0.767 | 0.733 | -0.034 |
| 延迟 p50 | 660 ms | 2106 ms | +219% |

**结论**：修复位置是「定义」而非「调用者」——调用者召回方向性错误。正确方向是「定义 vs 使用」加权：命中行是函数定义（而非调用/声明/注释）时才加分。基础设施（`symbols.py`、`--refine-symbols` 开关、`symbols` 可选 extra）保留供后续实验。

## 10. 复现

```bash
.venv/bin/repopilot eval \
  --dataset datasets/opencv-issues.jsonl \
  --repo /home/teddy/opencv
```

输出写入 `.repopilot/eval/<strategy>-body<N>.{json,md}`。JSON 里包含产生这组数字的完整配置（数据集、仓库、快照 commit、策略、正文预算、每关键词结果上限）和每个 case 的明细。**脱离配置的分数没有意义，所以两者存在同一个对象里。**

`--body-chars` 控制喂给检索器多少 issue 正文。OpenCV 的 issue 正文经常整段粘贴构建日志，所以「喂多少正文」本身是一个评测维度，而不是一个随手设的常量。
